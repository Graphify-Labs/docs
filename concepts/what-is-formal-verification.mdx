**Stop guessing which inputs to test.** Formal verification uses math to show code behaves a certain way for **every** input in scope, not just the ones you tested. When it can't, a good verifier gives you an input that breaks the claim.

## Tests sample. Reviews judge. Proofs cover.

Say you change a function that rounds prices.

| | Tells you | Misses |
| --- | --- | --- |
| <Icon icon="flask-conical" /> **Test** | The inputs you picked, like `9.995` and `0`, work. | Every input you didn't pick. |
| <Icon icon="eye" /> **Review** | Whether the code looks right, from a person or an AI. | It's an opinion, not a guarantee. |
| <Icon icon="sigma" /> **Proof** | No input in scope breaks the claim, or the one that does. | Anything outside its bounds. |

Use all three. Tests document intent, reviews catch design problems, and proofs cover cases nobody thought of.

## Prove against what you already have

<CardGroup cols={2}>
  <Card title="Write a spec" icon="file-text">
    A written rule, like "the result is never negative". Takes work, and most codebases don't have one.
  </Card>
  <Card title="Reuse the previous version" icon="history">
    "New returns the same as old for every input." Called **equivalence checking**. Needs no spec. **Graphify uses this.**
  </Card>
</CardGroup>

It fits refactors, performance work and agent-written code. The catch: if the old code had a bug, an equivalent new version has it too.

## Know where a proof stops

Verifiers limit input size, language features or time. A **bounded proof** holds within those limits, so there are more answers than pass and fail:

| Answer | In Graphify |
| --- | --- |
| Proved: no input in scope differs | **= Proven same** |
| Counterexample: this input differs | **≠ Behavior changed** |
| Sampled, none differed: evidence, not proof | **≈ No change found** |
| Couldn't decide: out of scope or budget | **? Not checked** |
| The check itself failed | **! Couldn't run** |

Graphify reports each one separately. It never turns "couldn't decide" into a pass.

## Turn a counterexample into a test

The distinguishing input gives you the exact arguments plus the old and new results. Use it to:

<Steps>
  <Step title="Reproduce">Run both versions on it.</Step>
  <Step title="Decide">Was the change intended, like a bug fix?</Step>
  <Step title="Pin it">Turn it into a regression test.</Step>
</Steps>
